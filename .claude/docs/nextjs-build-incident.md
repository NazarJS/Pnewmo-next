# Отчёт об устранении сбоя в среде сборки Next.js

> Исторический документ. Описывает инцидент, произошедший до перестройки проекта
> в монорепо. Сохранён потому, что объясняет, откуда в проекте взялась настройка
> `onlyBuiltDependencies`. Актуальное состояние сборки — в `.claude/CLAUDE.md`
> и `README.md`.

---

Этот отчет содержит сводную информацию о сбое, произошедшем при обновлении зависимостей проекта и миграции на Next.js, а также описывает предпринятые шаги, которые привели к полному восстановлению работоспособности среды разработки.

---

## 1. Описание возникших проблем

В процессе настройки и запуска проекта после обновления сборщика `pnpm` возникла цепочка взаимосвязанных сбоев, приведших к бесконечному циклу перезапусков и падению приложения:

### А. Запрос разрешений на сборку (`allowBuilds`) в `pnpm` v9
Сборщик `pnpm` заблокировал компиляцию нативных бинарных зависимостей (`sharp`, `@parcel/watcher`), требуя ручного подтверждения безопасности. Настройка некоторых из них в значение `false` привела к отсутствию необходимых скомпилированных C++ библиотек в `node_modules`.

### Б. Предупреждение об устаревшем API `module.register()` `[DEP0205]`
Node.js выдавал предупреждение в лог ошибок (`stderr`) при каждом запуске:
```text
[DEP0205] DeprecationWarning: `module.register()` is deprecated. Use `module.registerHooks()` instead.
```
Это предупреждение генерировалось пакетом `@tailwindcss/node@4.3.0` (Tailwind CSS v4), который использует ESM-загрузчики в новых версиях Node.js.

### В. Критический сбой (Panic) сборщика Turbopack в Rust
Основная причина бесконечного цикла перезапусков и зависаний заключалась в глубоком сбое внутри Rust-компилятора задач `Turbopack` в режиме разработки (`--turbo`):
```text
thread 'tokio-runtime-worker' panicked at turbopack/crates/turbo-tasks/src/manager.rs:1851:17:
cannot access a task-local storage value without setting it first
```
Многопоточный движок задач Turbopack падал при обработке CSS-компонентов Tailwind v4 на новых версиях Node.js. Из-за падения процесса терминал/IDE мгновенно запускал сервер заново, порождая бесконечную лавину логов `module.register()`.

## 2. Предпринятые действия для решения

Для полного устранения конфликтов и восстановления стабильности были выполнены следующие шаги:

1. **Полная очистка кэша и следов старой сборки:**
   * Удалена папка `node_modules` со старыми/недособранными бинарными файлами.
   * Удален устаревший файл блокировки зависимостей `pnpm-lock.yaml`.
   * Полностью удалена папка `.next` с поврежденным кэшем компилятора Turbopack (`rm -rf .next`).

2. **Корректная настройка доверия зависимостей в `package.json`:**
   В файл конфигурации проекта была внесена секция, одобряющая сборку нативных C++ модулей под текущую macOS:
   ```json
   "pnpm": {
     "onlyBuiltDependencies": [
       "@parcel/watcher",
       "sharp",
       "unrs-resolver"
     ]
   }
   ```

3. **Чистая установка зависимостей:**
   Запущена команда `pnpm install`, которая с нуля скачала пакеты и успешно скомпилировала бинарные зависимости без конфликтов безопасности.

4. **Turbopack — актуальное состояние на 2026-08-11:**
   Отключение Turbopack больше не требуется и не выполняется. В Next 16 он включён
   по умолчанию, и проект собирается на нём без сбоев: старая паника
   `turbopack/crates/turbo-tasks/src/manager.rs` не воспроизводится, dev-сервер
   стартует за ~900 мс на Node 24. Скрипт `dev` — обычный `next dev`, что и означает
   Turbopack. Откат на Webpack, если однажды понадобится: `next dev --webpack`.

   Исторически здесь было записано обратное — что `dev` переведён с `--turbo` на
   Webpack. На Next 16 это утверждение устарело и вводило в заблуждение.

---

## 3. Результат

После очистки кэша `.next` и корректной конфигурации доверия сборщика `pnpm` проект **успешно компилируется и запускается**.

* **Среда разработки:** Стабильна. Проект перестроен в монорепо на Turborepo — см. `README.md`.
* **Сборщик:** Turbopack, включён в Next 16 по умолчанию.
* **Tailwind CSS v4:** Работает корректно, компилирует стили без сбоев.
* **Производительность:** Оптимизация картинок через `sharp` функционирует на полной нативной скорости (prebuild-пакет `@img/sharp-darwin-arm64` на N-API).
