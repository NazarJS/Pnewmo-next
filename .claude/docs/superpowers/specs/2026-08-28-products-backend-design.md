# Этап 4a: бэкенд товаров

Дата: 2026-08-28
Ветка: `dev`
Предыдущий этап: `2026-08-11-categories-backend-design.md`
Парный этап: `2026-08-28-catalog-frontend-design.md`

## Зачем

Первые настоящие данные в проекте. До сих пор и категории, и товары были выдумкой: 40 категорий в сидах и 31 товар в `apps/web/db.json` придумывались под вёрстку. Этап заменяет их выгрузкой каталога Pneumax — 222 категории и 4842 товара, — заводит таблицу товаров и пять эндпоинтов CRUD.

Этап закрывает бэкенд целиком и проверяется `curl` и тестами. Перевод витрины на этот API вынесен в парный этап 4b: смешивать в одном плане новую таблицу с рекурсивной выборкой и перекладку четырёх страниц фронтенда значит отлаживать две незнакомые вещи одновременно.

## Объём

### Входит

1. Колонка `path` у `Category` — материализованный путь, и индекс под префиксный поиск.
2. Модель `Product`, миграция, индексы по `categoryId` и GIN по `specifications`.
3. Генератор фикстуры: скрипт, превращающий исходную выгрузку в компактный `catalog.json`.
4. Фикстура `catalog.json` в репозитории — 222 категории, 4842 товара.
5. Переписанный сид: идемпотентный, со сторожевым условием, заполняет обе таблицы.
6. `db:seed` в `pnpm dev`; отдельная команда `db:seed:reset` для принудительной перезаливки.
7. Пять роутов `product` в `packages/api-contract`, включая список с пагинацией и фильтром по категории.
8. Модуль `products` слоями: контроллер, сервис, репозиторий.
9. Поле `path` в `categorySchema` — оно понадобится фронтенду для хлебных крошек.
10. Тесты: e2e на HTTP-контур, юнит-тесты на расчёт пути, выборку поддерева и сторожевое условие.

### Не входит

1. Любые изменения в `apps/web`. Витрина переводится этапом 4b и до его завершения продолжает читать `json-server`.
2. Фасетные фильтры и подсчёт значений характеристик — этап 4c, отложен.
3. Аутентификация и авторизация. Решение задокументировано в разделе «Отложено осознанно».
4. Заполнение остатков (`quantity`, `unit`) и описаний. Колонки заводятся пустыми.
5. Связь товара с несколькими категориями. Обоснование — в разделе «Дубли».
6. Полнотекстовый поиск по товарам.

## Источник данных

Исходник — `pneumax_pnewmatica.json`, 7.7 МБ, дерево категорий с товарами на узлах. В репозиторий он **не** кладётся: после чистки от него остаётся 2.75 МБ, а хранить обе версии значит однажды перепутать, какая актуальна.

Замеры на выгрузке от 2026-08-28:

| Показатель | Значение |
|---|---|
| Узлов-категорий | 222 |
| Глубина дерева | 4 уровня |
| Товаров в исходнике | 4862 |
| Товаров после схлопывания дублей | 4842 |
| Из них с разбираемой ценой | 4838 |
| Уникальных ключей характеристик после чистки | 34 |

### Товары висят только на двух нижних уровнях

| Уровень | Узлов | Своих товаров |
|---|---|---|
| 1 (корень) | 1 | 0 |
| 2 | 6 | 0 |
| 3 | 34 | 1638 |
| 4 | 181 | 3224 |

Это определяющий факт для всей выборки. Если страница категории показывает только собственные товары, то семь категорий из 222 — включая **все шесть верхнего уровня** — открываются пустыми. А верхний уровень это ровно то, что человек видит в меню первым. Отсюда требование: выборка идёт по поддереву, и оно же диктует материализованный путь.

### Корень размечен неверно

Корневой узел называется `Гидравлика`, но его `url` — `/catalog/pnevmatika/`, а все шесть детей пневматические: цилиндры, распределители, клапаны, блоки подготовки воздуха, фитинги, аксессуары. Это ошибка в источнике.

**Решение: генератор переименовывает корень в «Пневматика».** Слаг берётся из `url` и уже равен `pnevmatika`, так что переименование лишь приводит имя в соответствие с адресом и содержимым. Правка живёт в генераторе явной строкой с комментарием, а не молча в данных: если следующая выгрузка приедет исправленной, строку надо будет снять, и она должна быть заметна.

### Что в данных мусор

Проверено на всех 4862 товарах, без исключений:

| Поле | Состояние | Что делаем |
|---|---|---|
| `description` | пусто у всех | колонку заводим, не заполняем |
| `aiDescription` | пусто у всех | колонку заводим, не заполняем |
| `characteristics.full` | пусто у всех | колонку заводим, не заполняем |
| `characteristics` у категорий | всегда `{"items": {}}` | игнорируем |
| `title` | всегда битая склейка | отбрасываем, берём `fullTitle` |
| `type` | всегда `"product"` | не заводим |

`title` заслуживает пояснения: это не «иногда грязное» поле, а всегда сломанное. Короткое название приклеено к `fullTitle` без разделителя, из-за чего строка выглядит так: `1391.63.0125.01 - Цилиндр пневматический силовой ISO 155521391.63.0125.01 - Цилиндр…`. Числа `15552` и `1391` слиплись. Восстановить границу склейки надёжно нельзя, а `fullTitle` содержит ту же информацию целиком — поэтому единственным названием становится он.

Из `characteristics.short` вычищаются пять ключей:

| Ключ | Товаров | Почему мусор |
|---|---|---|
| `Рейтинг` | — | метрика отзывов |
| `Сумма оценок` | — | метрика отзывов |
| `Количество проголосовавших` | — | метрика отзывов |
| `Название для 2GIS` | 81 | поле выгрузки в справочник, 80 уникальных значений из 81 |
| `Текст Alt Картинке` | 61 | SEO-атрибут картинки, 61 уникальное значение из 61 |

Общее у всех пяти: это метаданные CMS, попавшие в характеристики по недосмотру источника. Ни одно не описывает свойство товара. Оставить их значит однажды увидеть в фасетных фильтрах «выберите рейтинг от и до» и «выберите alt-текст» — с числом вариантов, равным числу товаров.

После чистки остаётся 34 уникальных ключа.

## Схема

### `path` у категории

```prisma
model Category {
  // ...существующие поля
  path String @unique
}
```

Формат — собственные идентификаторы через точку: `2`, `2.14`, `2.14.87`. Путь считается при вставке, когда идентификатор родителя уже известен: `path = parent.path + '.' + id`. Для корня это просто `id`.

Почему собственные id, а не слаги: слаг категории изменяем через админку, и переименование ломало бы путь у всего поддерева. Идентификатор неизменен.

Выборка поддерева:

```sql
WHERE path = $1 OR path LIKE $1 || '.%'
```

Первое условие берёт саму категорию, второе — потомков. Без первого страница категории теряла бы собственные товары.

### Индекс под префиксный поиск — не по умолчанию

Обычный btree-индекс по `text` в локали, отличной от `C`, **не используется** для `LIKE 'префикс%'`. Это классическая ловушка Postgres: индекс создан, план запроса его игнорирует, seq scan по таблице обнаруживается только под нагрузкой. Нужен индекс с классом операторов `text_pattern_ops`.

Prisma документирует запись `@@index([path(ops: raw("text_pattern_ops"))])`, но **на Prisma 7 это надо проверить до реализации** — по жёсткому ограничению №2 в `CLAUDE.md` примеры для шестой версии здесь не показатель. Порядок действий: сначала свериться с документацией через context7, при отсутствии поддержки — дописать `CREATE INDEX` строкой в файл миграции руками. Проверка результата одна и та же: `EXPLAIN` на запросе с `LIKE 'x.%'` должен показать `Index Scan`, а не `Seq Scan`.

### `Product`

```prisma
model Product {
  id                 Int      @id @default(autoincrement())
  externalId         String   @unique @map("external_id")
  categoryId         Int      @map("category_id")
  category           Category @relation(fields: [categoryId], references: [id], onDelete: Restrict)
  name               String
  imageUrl           String   @map("image_url")
  price              Decimal? @db.Decimal(12, 2)
  quantity           Decimal? @db.Decimal(12, 3)
  unit               String?
  description        String   @default("")
  aiDescription      String   @default("") @map("ai_description")
  specifications     Json     @default("{}")
  specificationsFull Json     @default("{}") @map("specifications_full")
  createdAt          DateTime @default(now()) @map("created_at")
  updatedAt          DateTime @updatedAt @map("updated_at")

  @@index([categoryId])
  @@map("products")
}
```

Решения по типам:

**`price` — `Decimal`, не `Float`.** Цена в рублях с копейками; двоичная плавающая точка даёт `21493.959999999999` там, где должно быть `21493.96`. Nullable, потому что у 4 товаров цена в источнике пуста, и `0` вместо неё соврал бы: ноль означает «бесплатно», а не «неизвестно».

**`quantity` — `Decimal(12,3)`, не `Int`.** В источнике остатки встречаются дробными: `29829.6 м`. Целочисленная колонка потеряла бы дробную часть. Заводится пустой.

**`unit` отдельно от `quantity`.** Исходное `available` неоднородно: 2055 записей в штуках, 64 в метрах, 2743 пусты. Разбирать это в одно число значит потерять единицу и утверждать, что 64 бухты кабеля лежат поштучно. Оба поля заводятся пустыми, заполнение — отдельная задача, когда появится источник остатков.

**`onDelete: Restrict` на связи с категорией.** Тот же выбор, что у дерева категорий: удаление категории с товарами должно падать явной ошибкой, а не уносить товары каскадом.

**GIN по `specifications`.** Нужен не сейчас, а этапу 4c: фасетные фильтры будут спрашивать `specifications @> '{"Производитель": "Италия"}'`. Индекс закладывается сразу, чтобы переезд фильтров не требовал новой миграции на таблице в 4842 строки.

`hasAiDescription` не заводится: значение выводится из `aiDescription`, а отдельная колонка означала бы два источника правды, которые однажды разойдутся.

### Дубли `externalId`

В источнике 20 товаров с повторяющимися идентификаторами — 4842 уникальных из 4862. Причина: один товар лежит в двух категориях.

**Решение: `externalId` уникален, дубли схлопываются, категория берётся от первого вхождения при обходе в глубину.** Осознанное упрощение. Честной моделью была бы связь многие-ко-многим, но она добавляет таблицу, усложняет выборку поддерева и подсчёт `total` — ради 0.4% записей. Если потеря вторых привязок начнёт мешать, переход на связующую таблицу не требует смены остальной схемы.

Схлопывание живёт в генераторе фикстуры, а не в сиде: сид должен вставлять данные, а не принимать решения об их качестве.

## Контракт

```ts
export const productSchema = z.object({
  id: z.number().int(),
  externalId: z.string(),
  categoryId: z.number().int(),
  name: z.string(),
  imageUrl: z.string(),
  price: z.string().nullable(),
  quantity: z.string().nullable(),
  unit: z.string().nullable(),
  description: z.string(),
  aiDescription: z.string(),
  specifications: z.record(z.string()),
  specificationsFull: z.record(z.string()),
});
```

`price` и `quantity` — строки, а не числа. Prisma отдаёт `Decimal`, и превращение его в JavaScript `number` возвращает ровно ту потерю точности, ради избежания которой выбран `Decimal`. Форматированием занимается фронтенд.

### Список

```ts
list: {
  method: 'GET',
  path: '/products',
  query: z.object({
    categoryId: z.coerce.number().int().positive().optional(),
    offset: z.coerce.number().int().gte(0).default(0),
    limit: z.coerce.number().int().gt(0).max(100).default(24),
  }),
  responses: { 200: z.object({ items: z.array(productSchema), total: z.number().int().gte(0) }) },
}
```

Форма `{ items, total }` и пара `offset`/`limit` взяты из `packages/api-contract/src/common.ts` проекта `panel-administration` — конвенция уже обкатана, и повторять её дешевле, чем изобретать свою.

`z.coerce` обязателен: параметры строки запроса приходят строками, обычный `z.number()` отверг бы любой корректный запрос.

**Потолок `limit` в 100 — не косметика.** Без него первый же обход бота с `?limit=100000` вытащит из базы всю таблицу и сериализует её в JSON. Значение по умолчанию 24 выбрано кратным трём и четырём: сетка карточек раскладывается без огрызка и на трёх, и на четырёх колонках.

Фильтр принимает `categoryId`, а не путь: клиенту незачем знать о материализации, раскрытие поддерева — забота сервера. Смена внутреннего представления пути не должна ломать фронтенд.

Остальные четыре роута — `getById`, `create`, `update`, `remove` — повторяют форму категорий, включая коды ошибок `404` и `409`.

## Слои модуля

Как в `categories`: контроллер тонкий, сервис содержит правила, репозиторий знает Prisma. Границы описаны в `2026-08-11-categories-backend-design.md`, раздел «Границы слоёв».

Единственное место с настоящей логикой — выборка списка:

1. Если `categoryId` задан, репозиторий читает `path` этой категории. Нет категории — `404`, а не пустой список: запрос к несуществующей категории это ошибка клиента, и молчаливый пустой ответ её прячет.
2. Товары выбираются джойном на категорию с префиксным условием по пути.
3. `findMany` и `count` выполняются **в одной транзакции**. Иначе между ними может пройти вставка, и `total` разойдётся со страницей — на глаз это выглядит как исчезающий последний товар.

## Сиды

### Генератор фикстуры

`apps/api/prisma/seed/build-catalog-fixture.mjs` — отдельный скрипт, читает исходную выгрузку, применяет все решения этого документа (чистка, схлопывание, переименование корня, расчёт путей) и пишет `catalog.json`.

Скрипт коммитится вместе с результатом. Причина: без него фикстура становится артефактом, который «Даниил один раз сконвертировал», и пересобрать её из новой выгрузки сможет только он. Со скриптом это воспроизводимая операция.

Форма фикстуры:

```json
{
  "categories": [{ "path": "1", "slug": "pnevmatika", "name": "Пневматика" }],
  "products": [{ "externalId": "3649", "categoryPath": "1.2.4", "name": "…",
                 "imageUrl": "…", "price": 21493.96, "specifications": {} }]
}
```

Пути в фикстуре — позиционные, они лишь задают структуру и порядок вставки. Настоящие пути из идентификаторов базы считаются сидом.

### Идемпотентность

Требование звучало как «залить один раз у всех, дальше не трогать». Текущий сид категорий делает обратное: начинается с `TRUNCATE ... RESTART IDENTITY CASCADE` и при каждом прогоне сносит всё.

**Решение: сторожевое условие.** Сид считает строки в `products`. Если их больше нуля — выходит, не тронув ничего. Пустая таблица бывает ровно один раз, сразу после миграции: тогда и заливаются обе таблицы.

Следствие, которое стоит проговорить как достоинство, а не как побочный эффект: **после первого товара, созданного через админку, сид больше не сработает никогда** и не сможет затереть введённое руками. Это ровно требуемое поведение.

Альтернатива — upsert по `externalId` на каждом старте — отвергнута дважды: 4842 upsert'а на каждый `pnpm dev` заметно замедлят запуск, и, что важнее, каждый старт молча возвращал бы к состоянию фикстуры любые правки из админки.

Для принудительной перезаливки заводится `pnpm db:seed:reset`: сносит обе таблицы и льёт заново, сторожевое условие игнорирует.

### Порядок вставки

1. Категории по возрастанию глубины — внешний ключ требует, чтобы родитель существовал. Путь считается сразу после вставки, когда идентификатор известен.
2. Товары пачками через `createMany`. Построчная вставка 4842 записей — это 4842 обращения к базе; пачками по 500 сид укладывается в единицы секунд.

`pnpm dev` получает вызов `db:seed` после `db:sync`.

## Тесты

**e2e на HTTP-контур** — против отдельной базы `pnewmo_test`, как описано в спеке этапа 3a. Покрывают пять роутов, пагинацию, фильтр по категории и `404` на несуществующей категории.

**Юнит-тесты:**

1. Расчёт пути при вставке дерева: у ребёнка путь равен пути родителя плюс собственный идентификатор.
2. Выборка поддерева включает саму категорию и всех потомков и не включает соседей. Тест обязан проверять обе половины условия — забытое `path = $1` даёт правдоподобную выдачу, в которой не хватает только собственных товаров категории.
3. Сторожевое условие: на непустой таблице сид не делает ни одной записи.
4. Схлопывание дублей в генераторе: из двух записей с одним `externalId` остаётся первая.

## Критерии готовности

1. `pnpm typecheck` и `pnpm build` зелёные.
2. `pnpm lint` для `@pnewmo/api` и `@pnewmo/api-contract` — чисто, без единого предупреждения.
3. `pnpm test` зелёный.
4. На чистой базе `pnpm dev` поднимает стек и заливает 222 категории и 4842 товара без ручных команд.
5. Повторный `pnpm dev` не меняет ни одной строки.
6. `GET /products?categoryId=<корень>&limit=1` возвращает `total` = числу товаров всего поддерева, а не нулю.
7. `EXPLAIN` на префиксном запросе по `path` показывает `Index Scan`.
8. `GET /products?limit=100000` отвергается валидацией, а не выгружает таблицу.

| `createMany` упрётся в размер запроса | вставка пачками по 500 |

## Отложено осознанно

1. **Аутентификация.** API открыт полностью: `POST /products` выполняется обычным `curl` без токена. Пока всё работает на localhost, это не эксплуатируемо. Перед первым выкатом в прод закрыть обязательно — риск уже зафиксирован в спеке этапа 3b, раздел «Риск: страница `/admin` доступна всем», и этот этап его не снимает, а расширяет на пишущие ручки товаров.
2. **Артикул отдельной колонкой.** У 1560 товаров из 4842 `name` начинается с артикула вида `1391.63.0125.01 - `. У остальных двух третей колонка была бы пуста, а надёжного признака артикула в данных нет. Артикул остаётся внутри названия.
3. **Остатки.** `quantity` и `unit` заводятся пустыми: источника остатков пока нет, а разбор `available` из выгрузки дал бы три разных смысла в одной колонке.
4. **Описания.** `description`, `aiDescription`, `specificationsFull` пусты у всех 4862 товаров источника. Колонки заведены, чтобы их появление не требовало миграции.
5. **Многие-ко-многим товар↔категория.** См. раздел «Дубли».
6. **Полнотекстовый поиск.** Поле поиска в хедере существует, но ищет по моку. Перевод — отдельная задача после 4b.
