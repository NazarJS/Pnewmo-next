# Этап 4b: перевод витрины на API, карточки товаров, админка

Дата: 2026-08-28
Ветка: `dev`
Предыдущий этап: `2026-08-28-products-backend-design.md`
Отменяет ограничение: `2026-08-12-categories-frontend-design.md`, раздел «Жёсткое ограничение: страницу каталога трогать нельзя»

## Зачем

Витрина до сих пор целиком живёт на `json-server`: и меню, и страница каталога, и карточка товара читают `apps/web/db.json` через порт 3001. Реальный API на 4000 не участвует нигде, кроме служебной страницы `/dev`.

После этапа 4a данные лежат в Postgres, и это состояние становится нерабочим: меню строилось бы по 40 выдуманным категориям, которых в базе больше нет, а ссылки вели бы в никуда. Поэтому этап переводит витрину на API целиком и выключает `json-server`.

Заодно закрывается расхождение, обнаруженное 2026-08-28: раздел «Состояние» в `CLAUDE.md` утверждал, что категория, созданная через API, попадёт в меню. Это было неверно — и меню, и страница каталога звали одну и ту же `fetchCategories`, смотрящую в мок.

## Объём

### Входит

1. `getQueryClient` — серверный клиент запросов на запрос, `cache(makeQueryClient)`.
2. Сущность `product` во фронтенде: типы, билдеры ключей и query, клиентские хуки, серверный префетч.
3. Перевод `useCategories` с `useEffect` на `tsr.categories.list.useQuery`.
4. Страница каталога `/catalog/[slug]`: серверный рендер, префетч с гидрацией, карточки, пагинация.
5. Кеширование данных через `unstable_cache` с тегами и сбросом из мутаций.
6. Страница товара `/product/[id]` — перевод на реальный API.
7. Страница `/admin`: форма создания категории и форма создания товара.
8. Выключение `json-server`: из `turbo.json`, скриптов, `pnpm dev`; удаление `db.json`.
9. Отцепление панели фильтров от страниц с сохранением кода — под этап 4c.
10. Тесты: разбор пагинации из URL, стабильность ключей, маппинг категорий.

### Не входит

1. Фасетные фильтры — этап 4c.
2. Дизайн. Вёрстка карточек минимальная и заведомо временная: сетка, картинка, название, цена. Это осознанное требование заказчика, а не недоработка.
3. Аутентификация `/admin` — см. «Отложено осознанно».
4. Редактирование и удаление через админку. Формы только создают; `update` и `remove` в API есть, интерфейса к ним нет.
5. Перевод поиска в хедере — он до сих пор ищет по моку.

## Отмена ограничения этапа 3b

Спека 3b содержала пункт «страницу каталога трогать нельзя»: она принадлежала зоне активной разработки коллеги, и правки там дали бы конфликты при вливании из репозитория NazarJS.

Ограничение снимается, и вот почему это безопасно именно сейчас. Работа коллеги влита 2026-08-27 мерджем `fa46b64`, ветка `New-branch` в него уже вошла. Страница каталога после этого мерджа переписана им же под `<Suspense>` — то есть его правки в этом файле завершены, а не в процессе. Наши изменения ложатся поверх законченной работы, а не поперёк идущей.

Панель фильтров, которую он строил, отцепляется, но не удаляется — см. раздел «Парковка фильтров».

## Раскладка кода

Конвенции берутся из `panel-administration` — проекта того же автора на том же стеке (Next, ts-rest, TanStack Query). Повторять обкатанную раскладку дешевле, чем изобретать свою.

```
entities/product/
  index.ts              баррель: lib + api/hook, но НЕ prefetch
  lib/types.ts          типы фильтра и состояния
  lib/constants.ts      константы: размер страницы, допустимые лимиты
  lib/queryKey.ts       билдер ключа и билдер query — общие для хука и префетча
  api/hook.ts           'use client', клиентские хуки
  api/prefetch.ts       серверный префетч, server-only
```

**`api/prefetch.ts` намеренно не реэкспортируется из барреля.** В `panel-administration` это зафиксировано комментарием в `entities/viewer/index.ts`: серверный код, утёкший в клиентский бандл через баррель, тянет за собой зависимости, которые в браузере не работают, и ломается не на сборке, а в рантайме.

Константы живут в `lib/constants.ts`, чистые функции — в `lib/`, и ни то ни другое не смешивается с компонентами. Компоненты — `export default` снизу файла, хуки — именованный экспорт; это уже зафиксировано скиллом `component-structure` и здесь лишь повторяется.

## Ключи запросов

Самая ценная вещь, унесённая из `panel-administration`, — форма билдера ключа.

```ts
export type ProductListQueryKey = readonly ['product-list', number | null, number, number];

export const buildProductListQueryKey = (filter: ProductListFilterState): ProductListQueryKey =>
  ['product-list', filter.categoryId ?? null, filter.offset, filter.limit];

export const buildProductListQuery = (filter: ProductListFilterState) => ({
  categoryId: filter.categoryId ?? undefined,
  offset: filter.offset,
  limit: filter.limit,
});
```

**Ключ — позиционный массив с явным перечислением полей, а не `JSON.stringify(filter)`.** Причина скопирована из оригинала дословно, потому что она неочевидна и дорога: у `JSON.stringify` результат зависит от порядка полей объекта. Два семантически одинаковых фильтра, собранных в разном порядке — сервером в префетче и клиентом в хуке, — дают разные строки. Страница при гидрации молча уходит за данными второй раз. Позиционный массив читает поля по имени, и порядок в объекте-источнике роли не играет.

**`buildProductListQuery` — единственная точка сборки query из фильтра**, общая для хука и префетча. Два независимых маппинга однажды разойдутся — достаточно забыть поле при добавлении фильтра, — и под одинаковым ключом закэшируется другая выдача. Заметить это в Network невозможно: лишнего запроса не будет, просто данные окажутся не те.

На парность ключа и query пишется юнит-тест: он вызывает оба билдера на одном фильтре и проверяет, что ключ содержит ровно те поля, что ушли в query.

## Кеширование: почему не `revalidate` на странице

Первоначально предполагалось поставить `export const revalidate` на страницу каталога и получить ISR. **Это не работает для страницы с `searchParams`**, и проверено по исходникам Next 16.2.

При пререндере `searchParams` подменяется «висящим» промисом, который никогда не резолвится. Пока его не разворачивают, страница остаётся статической. Первое же `await searchParams` помечает доступ динамическим (`annotateDynamicAccess`) и выбивает страницу из статической оболочки. А пагинация без чтения `searchParams` невозможна.

**Решение: кешируем данные, а не роут.** Выборка товаров оборачивается в `unstable_cache` с параметрами в ключе и тегами:

```ts
const getCachedProducts = unstable_cache(
  async (categoryId: number, offset: number, limit: number) => { /* запрос к API */ },
  ['product-list'],
  { tags: ['products'], revalidate: 300 },
);
```

Что это даёт: HTML собирается на каждый запрос — боты получают полную разметку, — но поход в базу выполняется раз в пять минут на комбинацию параметров. Мутации админки зовут `revalidateTag('products')`, и выдача обновляется немедленно, не дожидаясь истечения срока.

Директива `'use cache'` из Next 16 решала бы ту же задачу элегантнее, но требует включения `cacheComponents` на весь проект. Это отдельное решение с последствиями для всех страниц, и принимать его внутри задачи про каталог неправильно. `unstable_cache` — стабильный путь, переход на `'use cache'` позже не потребует менять форму кода.

## Страница каталога

```
/catalog/[slug]?page=2
```

Порядок работы Server Component:

1. Читает `slug` из `params` и `page` из `searchParams`.
2. Разбирает пагинацию чистой функцией (см. ниже), получает `offset` и `limit`.
3. Находит категорию по слагу, отдаёт `notFound()`, если её нет.
4. Через `getQueryClient` префетчит список тем же билдером ключа, что использует клиентский хук.
5. Оборачивает поддерево в `HydrationBoundary` с `dehydrate(queryClient)`.

Клиентский компонент списка берёт данные из `useQuery` — они уже в кэше, повторного запроса нет. `staleTime` в 60 секунд из `makeQueryClient` это гарантирует.

Инфраструктура под такой префетч уже написана коллегой и ждала применения: в `makeQueryClient` настроен `dehydrate.shouldDehydrateQuery` с пропуском `pending`-запросов — это конфигурация из гайда TanStack по потоковому SSR. Не хватало только `getQueryClient`, и он появляется здесь.

### Пагинация выводится из URL

`useState` для номера страницы не заводится. Номер и размер пересчитываются из адреса на каждом рендере — тогда «назад» и «вперёд» в браузере возвращают вместе с адресом и страницу списка, а ссылку на третью страницу можно отправить коллеге.

Разбор — чистой функцией, а не выражением в теле компонента, и **одной и той же на сервере и на клиенте**. Расхождение здесь означает, что сервер отрендерил одну страницу, а клиент после гидрации показал другую.

Правило берётся из `panel-administration`, `shared/hooks/table/utils/pagination.ts`, вместе с ловушкой, ради которой оно там появилось: `Number('Infinity')` даёт `Infinity`, и наивная проверка `raw > 0` его пропускает. Поэтому условие — `Number.isFinite(raw) && raw > 0`, иначе дефолт.

Дефолтные значения в адрес не пишутся: первая страница остаётся чистым `/catalog/slug`, без `?page=1`. Это важно и для SEO — два адреса с одинаковым содержимым породили бы дубль.

Смена размера страницы всегда возвращает на первую: третьей страницы при новом лимите может не существовать.

### Карточки

Сетка, картинка, название, цена, ссылка на товар. Никакого дизайна — заказчик явно сказал, что вёрстку будут переделывать, и вкладываться в неё сейчас значит выбросить работу.

Два содержательных требования всё же есть. Картинки приходят с CDN pneumax — внешний домен надо прописать в `images.remotePatterns`, иначе `next/image` откажется их отдавать. И цена приходит строкой (`Decimal` не переживает превращения в `number`), поэтому форматируется на месте через `Intl.NumberFormat` с рублём.

## Меню

`useCategories` переписывается на `tsr.categories.list.useQuery` и переезжает в `entities/category/api/hook.ts`. Ключи — в `entities/category/lib/queryKey.ts`.

Компонент `HeaderCatalog` при этом не меняется: он получает тот же `{ categories, loading, error }`. Приём взят из спеки 3b, раздел «Перевод хедера: меняем хук, а не компонент», и остаётся верным.

Побочная выгода: две ошибки `react-hooks/set-state-in-effect` из baseline линтеров живут именно в связке `useCategories` + `HeaderCatalog`. Переезд на `useQuery` убирает первопричину — `setState` в теле эффекта.

**Уточнение 2026-08-31.** Утверждение выше не подтвердилось. Обе ошибки `react-hooks/set-state-in-effect` живут в `HeaderCatalog.tsx` — это `setCatalogActive` и `setMobileCategoryActive`, вызываемые из тела двух `useEffect`, управляющих открытием каталога (сейчас строки 60 и 68), а не в удалённом `useCategories`. К хуку на `useEffect`, который переезд убрал, они отношения не имели. Переезд на `useQuery` первопричину не убрал, и baseline остался прежним: `lint:js` по-прежнему даёт 2 ошибки. Это уже зафиксировано в `.claude/docs/superpowers/specs/2026-08-11-monorepo-infra-design.md`, раздел «Переизмерено 2026-08-29», и в плане этапа (коммит `ecda56d`); здесь фиксируется то же для самой спеки.

**Маппинг обязателен.** API отдаёт `parentId`, фронтенд ожидает `parent_id`, а поле `url` вычисляется из слага и в API его нет вовсе. Существующая `fetchCategories` этот маппинг делает; при переезде он должен переехать вместе с ней, иначе дерево соберётся пустым. Спека 3b отдельно отмечала это как неочевидное место.

Категории префетчатся в layout: меню есть на каждой странице.

## Страница товара

`/product/[id]` переводится на `getById`. Минимально: картинка, название, цена, таблица характеристик из `specifications`. Без этого перевода страница умрёт вместе с `json-server`.

## Админка

`/admin` — две формы, `react-hook-form`, мутации через `tsr`.

**Форма категории**: название, слаг, выбор родителя из плоского списка с отступами по глубине. Валидация приходит с сервера — в контракте у слага regex со своим текстом ошибки, написанным для человека («Допустимы только строчные латинские буквы, цифры, дефис и подчёркивание»). Дублировать правило на клиенте не нужно: два источника правды разойдутся.

**Форма товара**: категория, название, ссылка на картинку, цена. `specifications` вводится как пары ключ-значение, минимальным интерфейсом. Остальные колонки формой не заполняются — они и сидом не заполняются.

После успешной мутации:

1. `invalidateQueries` по ключу списка — обновляет клиентский кэш.
2. `revalidateTag('products')` или `revalidateTag('categories')` — сбрасывает серверный кеш данных, иначе витрина будет отдавать старое до истечения пяти минут.

Второй шаг легко забыть, и его отсутствие проявляется не сразу — товар создан, в админке виден, а на витрине появится через пять минут. Поэтому он вынесен в отдельную серверную функцию, вызываемую из `onSuccess`.

## Выключение json-server

Убирается из `turbo.json` (таска `mock`), из скриптов `apps/web/package.json`, из `pnpm dev`. Файл `db.json` удаляется, зависимость `json-server` — из `devDependencies`.

Проверка полноты: после удаления в `apps/web/src` не должно остаться ни одного вхождения `localhost:3001`.

## Парковка фильтров

`ProductFilterPanel`, `products.api.ts`, `buildFilterQueryParams`, `buildCategoryPath` и парсеры фильтров остаются в репозитории, но отцепляются от страниц.

Причина, по которой их нельзя просто оставить работающими: они построены под движок запросов `json-server`, что зафиксировано в спеке коллеги отдельным разделом «Поправка №2 — реальный API json-server отличается от того, что предполагала спека». С выключением мока источник исчезает.

Причина, по которой их нельзя просто удалить: это законченная работа коллеги недельной давности, и в ней есть ценное — форма `specifications: Record<string, string>` совпадает с нашей колонкой один в один, а `buildCategoryPath` предвосхищает материализованный путь.

Условие корректности парковки: `pnpm typecheck` и `pnpm build` обязаны оставаться зелёными. Отцепленный код не должен ссылаться на удалённые модули.

Переезд описан отдельно — `2026-08-28-product-filter-migration-design.md`.

## Тесты

1. **Разбор пагинации** — чистая функция, включая `?page=Infinity`, `?page=0`, `?page=-1`, `?page=abc` и отсутствие параметра. Зеркалит `pagination.spec.ts` из `panel-administration`.
2. **Парность ключа и query** — на одном фильтре оба билдера согласованы; ключ не зависит от порядка полей в объекте-источнике.
3. **Маппинг категорий** — `parentId` → `parent_id`, `url` собирается из слага. Тест на то, что дерево из ответа API строится непустым.
4. **Форматирование цены** — строка `"21493.96"` превращается в рубли без потери копеек.

1. `pnpm typecheck` и `pnpm build` зелёные.
2. `pnpm lint`: две ошибки `react-hooks/set-state-in-effect` исчезают. Baseline становится чище, и его надо переписать в `CLAUDE.md` и в спеке этапа 1.

## Риски

| Риск | Как обрабатываем |
|---|---|
| Ключ префетча разойдётся с ключом хука — тихий повторный запрос | общий билдер и юнит-тест на парность |
| Забыт `revalidateTag` в мутации | вынесен в отдельную функцию; критерий готовности №9 проверяет явно |
| `next/image` не пропустит CDN pneumax | домен в `images.remotePatterns`; проверяется на первой же карточке |
| Отцепление фильтров уронит сборку | критерий готовности №1; парковка делается отдельным коммитом |
| `unstable_cache` отдаёт устаревшее в разработке | `revalidate` берётся из переменной окружения, в dev — ноль |
| Потеря копеек при выводе цены | цена ходит строкой от Postgres до `Intl.NumberFormat`, в `number` не превращается |

## Отложено осознанно

1. **Аутентификация `/admin`.** Страница открыта всем, пишущие ручки API — тоже. Решение принято заказчиком осознанно: пока проект живёт на localhost, это не эксплуатируемо. Перед первым выкатом в прод закрыть обязательно. Риск зафиксирован здесь, в спеке 3b и в спеке 4a — три раза, потому что цена ошибки высока.
2. **Дизайн карточек.** Вёрстка временная по прямому требованию заказчика.
3. **Редактирование и удаление в админке.** API умеет, интерфейса нет.
4. **Поиск.** Поле в хедере остаётся неподключённым.
5. **`'use cache'` вместо `unstable_cache`.** Требует включения `cacheComponents` на весь проект — отдельное решение.
6. **Хлебные крошки.** Поле `path` в контракте для них уже есть, сами крошки не делаются.
