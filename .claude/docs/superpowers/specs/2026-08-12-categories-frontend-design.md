# Этап 3b: слой запросов, админ-страница, перевод хедера

Дата: 2026-08-12
Ветка: `dev`
Предыдущий этап: `2026-08-11-categories-backend-design.md`

## Зачем

Бэкенд категорий готов и проверен `curl`. Этап подключает к нему фронтенд: слой
кеширования запросов, страница администрирования с формой и переводит меню каталога с
рукописного хука на реальный API.

## Объём

### Входит

1. Слой TanStack Query: фабрика `QueryClient`, request-scoped клиент для серверных
   компонентов, провайдер, devtools.
2. Типизированный клиент `tsr` на `@ts-rest/react-query/v5`.
3. Фабрика ключей запросов.
4. Страница `/admin/categories`: дерево категорий, форма создания с выбором родителя,
   удаление.
5. Мутации создания и удаления с инвалидацией кеша.
6. Серверный префетч списка категорий со стримовой дегидратацией.
7. Перевод `useCategories` на реальный API — **без правки** `HeaderCatalog.tsx`.

### Не входит

- **Перевод `/catalog/[slug]` на реальный API.** Обоснование ниже, это жёсткое
  ограничение, а не отложенная задача.
- Обновление категории через интерфейс. Эндпоинт `update` существует и покрыт тестами,
  но форма редактирования — отдельная задача; в этой странице только создание и удаление.
- Авторизация страницы `/admin`. Её нет во всём проекте; риск зафиксирован ниже.
- Библиотека форм. Три поля обходятся без неё, обоснование ниже.
- Экспериментальный пакет `@tanstack/react-query-next-experimental`. Стриминг достигается
  стабильными средствами, см. соответствующий раздел.

## Жёсткое ограничение: страницу каталога трогать нельзя

`apps/web/src/app/catalog/[slug]/page.tsx` читает из json-server и категории, и товары,
затем фильтрует товары по `category_id` через `getChildCategoryIds`.

Идентификаторы в Postgres и в моке **не совпадают**. Замер на текущих данных: совпало 7
из 40, разошлось 33. Примеры: `pnevmaticheskie_klapany` — мок `16`, Postgres `6`;
`sistemy_dvukhlineynogo_deystviya` — мок `6`, Postgres `11`.

Причина: сиды вставляют категории по возрастанию глубины с автоинкрементом, а в моке
идентификаторы расставлены в другом порядке.

Следствие: если перевести на реальный API **только категории** этой страницы, она станет
фильтровать товары мока по идентификаторам Postgres и покажет **чужие товары** — молча,
без ошибки. Поэтому страница остаётся целиком на json-server до этапа 4, когда товары
переедут вместе с ней.

`apps/web/src/entities/category/api/category.api.ts` продолжает обслуживать эту страницу и
менять его нельзя. В файл добавляется комментарий с объяснением, чтобы следующий читатель
не «починил» его из лучших побуждений.

## Перевод хедера: меняем хук, а не компонент

`HeaderCatalog.tsx` — файл в зоне активной разработки NazarJS (см. спеки от 2026-07-20).
Правка в нём даст конфликт при merge.

Этого можно избежать полностью. `useCategories` возвращает `{ categories, loading, error }`,
и компонент использует только эту форму. Значит меняется **реализация хука**, а публичная
форма сохраняется — и `HeaderCatalog.tsx` остаётся нетронутым.

```ts
// было: useState + useEffect + fetch к json-server
// станет: tsr.categories.list.useQuery(...) с той же возвращаемой формой
export const useCategories = (): {
  categories: Category[];
  loading: boolean;
  error: string | null;
};
```

Побочная выгода: пропадает перезапрос при каждом монтировании, появляется кеш и
дедупликация — при том, что диff ограничен одним файлом.

### Маппинг обязателен, и он неочевиден

Фронтендовый тип и DTO контракта расходятся по трём полям:

| `entities/category/model/types.ts` | DTO контракта |
|---|---|
| `parent_id: number \| null` | `parentId: number \| null` |
| `path: string` | нет |
| `url: string` | нет |

**Ключевое: `parent_id` в snake_case.** `buildCategoryTree` и `getChildCategoryIds` читают
именно `category.parent_id`. Если хук вернёт объекты с `parentId`, дерево **соберётся
пустым** — все узлы окажутся без родителей и без корней, а ошибки не будет ни одной:
меню просто окажется пустым.

Поэтому хук маппит явно: `parentId` → `parent_id`, `url` достраивается как
`/catalog/${slug}`, `path` остаётся пустой строкой — оно не читается нигде, кроме
мок-данных.

Альтернатива — привести `types.ts` к camelCase — затронула бы и `HeaderCatalog.tsx`, и
страницу каталога, то есть файлы NazarJS. Маппинг в одном хуке дешевле.

## Слой запросов

Портируется конфигурация из рабочего проекта `panel-administration` с изъятием того, чего
здесь нет.

### Что переносится

| Файл | Содержание |
|---|---|
| `shared/lib/queryClient.ts` | `makeQueryClient()`: `staleTime`, `gcTime`, политика повторов, конфигурация дегидратации, глобальная обработка ошибок |
| `shared/lib/getQueryClient.ts` | `cache(makeQueryClient)` — request-scoped клиент для серверных компонентов |
| `shared/api/tsr.ts` | `initTsrReactQuery(contract, { baseUrl })` |
| `shared/providers/ReactQueryProvider.tsx` | браузерный singleton, `QueryClientProvider`, `tsr.ReactQueryProvider`, devtools в разработке |

Политика повторов переносится как есть: 4xx не повторяются, потому что это
детерминированные ответы — валидация, доступ, отсутствие записи. Повтор такого запроса
даст тот же результат и только задержит показ ошибки.

### Что не переносится

Sentry, `notify`/sonner, BFF-прокси на `/api/v1`, HttpOnly-cookie и редирект на `/login`
при 401, `bffLogger`, генерация `x-request-id`. Всего этого в проекте нет, и тащить
инфраструктуру под несуществующую задачу — то самое преждевременное усложнение.

Глобальная обработка ошибок сохраняет **форму** оригинала — `isTsRestError` плюс
`QueryCache`/`MutationCache` с `onError` — но вместо отправки в Sentry и показа тоста
пишет в консоль. Место для подключения сервиса остаётся явным.

### Стриминг без экспериментального пакета

`@tanstack/react-query-next-experimental` не используется. Стриминг достигается двумя
стабильными средствами, доступными с TanStack Query v5.40:

```ts
dehydrate: {
  shouldDehydrateQuery: (query) =>
    defaultShouldDehydrateQuery(query) || query.state.status === 'pending',
  shouldRedactErrors: () => false,
}
```

плюс префетч **без** `await` в серверном компоненте. Документация формулирует прямо:
начиная с 5.40 незавершённые запросы можно дегидратировать и отправлять клиенту, что
позволяет начать префетч, не блокируя рендер, и данные дотекают по готовности.

`shouldRedactErrors: () => false` переносится вместе с обоснованием из оригинала: Next
редактирует ошибки сам через digest, а повторная редакция на нашей стороне ломает
определение динамических страниц при отклонении стримящегося префетча.

### Ключи запросов задаются руками

В `@ts-rest/react-query/v5` ключ передаётся явно: `useQuery({ queryKey: ['categories'] })`.
Автоматической генерации нет, поэтому довод «ключи не могут разойтись» к этой библиотеке
не относится — выигрыш в типизации запроса и ответа и в едином месте для `baseUrl`.

Совпадение ключей между серверным префетчем и клиентским запросом обязательно: разошлись
хоть на символ — клиент не найдёт данные в кеше и сделает второй запрос **молча**, без
ошибки, только с лишним сетевым вызовом и миганием загрузки.

Поэтому ключи живут в одном модуле `entities/category/model/keys.ts`:

```ts
export const categoryKeys = {
  all: ['categories'] as const,
  list: () => [...categoryKeys.all, 'list'] as const,
};
```

## React 19 и `@ts-rest/react-query`

Пакет объявляет `peerDependencies: { react: "^16.8.0 || ^17.0.0 || ^18.0.0" }` — в обеих
версиях, и в стабильной 3.52.1, и в `3.53.0-rc.1`. React 19 не заявлен ни одной.

Рабочий проект `panel-administration` работает на React 18.2 и подтверждением не служит.

План проверяет совместимость **первым шагом**, до написания страницы: устанавливаем,
пишем один запрос, гоняем. Заработало — идём дальше. Нет — откат на `useQuery` из
TanStack Query с вызовом ts-rest-клиента внутри `queryFn`; типы при этом всё равно из
контракта, теряется только типизированная обёртка.

## Страница администрирования

Маршрут `/admin/categories` в `apps/web`, отдельного приложения не создаётся.

Раскладка по слоям соответствует скиллу `component-structure`:

```
apps/web/src/
├── app/admin/categories/page.tsx        серверный компонент: префетч + HydrationBoundary
└── features/category-admin/
    ├── ui/CategoryAdmin.tsx             композиция: форма + дерево
    ├── ui/CategoryForm.tsx              создание
    ├── ui/CategoryTree.tsx              список деревом с кнопкой удаления
    └── hooks/useCategoryMutations.ts    create, delete, инвалидация
```

Слой `features` вводится впервые: `entities` описывает данные, `widgets` — секции
страницы, а действия пользователя над сущностью — это `features`.

### Форма без библиотеки форм

Три поля: `name`, `slug`, `parentId`. Проверка выполняется схемой `createCategorySchema`
**из контракта** — той же, которой валидирует сервер:

```ts
const parsed = createCategorySchema.safeParse({ name, slug, parentId });
```

Это не только экономит зависимость, но и показывает главное свойство контракта: одна схема
работает на обеих сторонах. `react-hook-form` с `zodResolver` уместен, когда полей
становится много и появляются зависимые поля; на трёх полях он добавил бы зависимость и
слой абстракции без выгоды.

Сообщения об ошибках берутся из `issues` ответа API и из результата локального разбора.
Пользователь видит текст, объясняющий правило: для `slug` — «Допустимы только строчные
латинские буквы, цифры, дефис и подчёркивание».

### Выбор родителя

`select` со списком всех категорий, отступами по уровню вложенности, плюс вариант
«корневая категория» со значением `null`. Дерево для отступов строит существующий
`buildCategoryTree`.

### Дерево и удаление

Список отрисовывается деревом с отступами. У каждой категории кнопка удаления.

Удаление корневой категории с потомками вернёт 409 с сообщением «Нельзя удалить
категорию: у неё N подкатегорий» — это ожидаемый и полезный сценарий: он наглядно
показывает, зачем в схеме `onDelete: Restrict`.

Подтверждение удаления реализуется **не** через `window.confirm`: браузерный диалог
блокирует поток и мешает автоматизации. Вместо него — переключение кнопки в состояние
«Точно удалить?» повторным нажатием.

### Инвалидация после мутаций

После успешного создания или удаления инвалидируется `categoryKeys.all`. Оптимистичные
обновления не делаются: список из сорока элементов перезапрашивается мгновенно, а
оптимистичное обновление дерева с проверкой инвариантов на клиенте — источник
рассинхрона.

## Риск: страница `/admin` доступна всем

Авторизации в проекте нет, поэтому `/admin/categories` открыт любому, кто знает адрес, и
позволяет удалять категории. Для локальной разработки это приемлемо.

Перед любым выходом в сеть — включая тестовый стенд — страница должна быть закрыта. Это
фиксируется как явное условие этапа деплоя, а не как «потом разберёмся».

## Тесты

Юнит-тестов на фронтенде в проекте пока нет, и вводить инфраструктуру ради этого этапа
преждевременно. Проверка выполняется:

1. `pnpm typecheck` — контрактные типы обязаны сходиться;
2. проверкой в браузере по списку сценариев из критериев готовности;
3. проверкой того, что серверный префетч работает: в сетевой панели при загрузке
   `/admin/categories` **не должно** быть клиентского запроса к `/categories`, потому что
   данные пришли дегидратированными.

Третий пункт — единственный способ отличить работающий префетч от неработающего:
страница выглядит одинаково в обоих случаях.

## Критерии готовности

1. `/admin/categories` открывается и показывает 40 категорий деревом с отступами.
2. Создание категории с выбранным родителем добавляет её в дерево без перезагрузки
   страницы.
3. Создание с занятым `slug` показывает сообщение о конфликте, категория не создаётся.
4. Создание со `slug` в верхнем регистре показывает сообщение про допустимые символы —
   до отправки запроса, локальным разбором схемы.
5. Удаление листа убирает его из дерева.
6. Удаление категории с потомками показывает сообщение с количеством подкатегорий.
7. Меню каталога в шапке работает и берёт данные из Postgres: остановка `json-server`
   (`pnpm --filter @pnewmo/web mock` не запущен) на меню не влияет.
8. При загрузке `/admin/categories` клиентского запроса к `/categories` в сетевой панели
   нет.
9. `HeaderCatalog.tsx` в диффе этапа отсутствует.
10. `/catalog/gidravlika` и `/product/1` продолжают работать от json-server.
11. `pnpm typecheck` и `pnpm build` зелёные; `pnpm lint` без ошибок сверх baseline.
12. `pnpm --filter @pnewmo/web lint:js` не добавляет ошибок к двум существующим в
    `HeaderCatalog.tsx`.

## Риски

| Риск | Обработка |
|---|---|
| `@ts-rest/react-query` не работает на React 19 | проверяется первым шагом плана; откат на `useQuery` с ts-rest-клиентом в `queryFn` |
| Ключи серверного префетча и клиентского запроса разойдутся | ключи только из `categoryKeys`; критерий готовности №8 это ловит |
| Правка `useCategories` меняет форму возврата и ломает `HeaderCatalog.tsx` | форма фиксирована в спеке; критерий готовности №9 требует отсутствия файла в диффе |
| Дегидратация незавершённых запросов не сработает на Next 16 | проверяется критерием №8; при отказе префетч выполняется с `await` — стриминг теряется, работоспособность нет |
| CORS отклонит запросы браузера к API | `WEB_ORIGIN` в `apps/api/.env` уже указывает на `http://localhost:3000`, CORS настроен в `main.ts` |
| Категория, созданная в админке, не открывается в каталоге | ожидаемо и задокументировано: каталог до этапа 4 читает мок |

## Отложено осознанно

- Редактирование категории через интерфейс: эндпоинт `update` готов, форма — отдельная
  задача.
- Оптимистичные обновления.
- Библиотека форм: вводится, когда появится форма товара с характеристиками.
- Фронтенд-ревьюер из этапа 2: пишется после этого этапа, когда появится реальный код
  запросов и мутаций.
