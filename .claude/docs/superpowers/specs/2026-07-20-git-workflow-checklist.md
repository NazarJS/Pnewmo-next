# Чеклист: как пушить к главному разработчику без fork'а и не запутаться

## Контекст

Сегодня разбирались, почему "пропали" запушенные изменения. Причина — по невнимательности:

1. Переключились на `Stas/PR-for-Nazz`.
2. Слили изменения главного разработчика в свою ветку: `git merge upstream/Nazz`.
3. Запушили результат **напрямую в его репозиторий**: `git push upstream HEAD:Nazz`.

Так работать нельзя — `upstream` (`NazarJS/Pnewmo-next`) должен быть только источником для чтения (fetch/merge), а не местом, куда вы пишете напрямую. Дальше — чеклист, который убирает саму возможность повторить эту ошибку.

## Проверено: fork или нет

Через GitHub API подтверждено: `Baldezhnik232/Pnewmo-next` (`origin`) — это **не официальный fork** `NazarJS/Pnewmo-next` (`upstream`), это два независимых репозитория с общей историей коммитов (`fork: false` у обоих). Из-за этого GitHub не покажет автоматическую кнопку "Compare & pull request" — но PR между ними всё равно возможен через ручную compare-ссылку, т.к. общая история есть.

Разобрали два варианта:
- **Сделать настоящий fork** — штатный опыт (кнопки/`gh pr create` из коробки), но требует переименования/удаления текущего `origin` и переforkивания заново — это необратимое действие с общим состоянием, вручную не делаем.
- **Оставить как есть, PR через compare-URL** (выбрано) — без операций с репозиторием, `upstream` становится read-only.

## Настройка (один раз, уже готово)

Remotes уже настроены верно, менять не нужно:
```bash
git remote -v
# origin    https://github.com/Baldezhnik232/Pnewmo-next.git (ваш репозиторий)
# upstream  https://github.com/NazarJS/Pnewmo-next.git (репозиторий главного разработчика)
```

**Правило:** `upstream` — только `fetch`/`merge`. Команда `git push upstream ...` в этом процессе больше не используется никогда.

## Чеклист: от новой фичи до PR

1. **Обновить upstream перед началом работы:**
   ```bash
   git fetch upstream
   ```

2. **Создать свою ветку от актуального `upstream/Nazz`** (не от старой локальной копии):
   ```bash
   git checkout -b <ваша-ветка> upstream/Nazz
   ```
   Если продолжаете существующую ветку — подтянуть актуальные изменения слиянием, не пушем:
   ```bash
   git checkout <ваша-ветка>
   git merge upstream/Nazz
   ```

3. **Работать и коммитить как обычно** в `<ваша-ветка>`.

4. **Пушить только в `origin`** (свой репозиторий), никогда в `upstream`:
   ```bash
   git push -u origin <ваша-ветка>
   ```
   `-u` нужен один раз на ветку — дальше просто `git push`. Отсутствие `-u` при первом пуше — вероятная причина, почему `Stas/Feature-new` вчера не улетела на `origin` (git молча требует `-u`/явный `origin <branch>` для новой ветки, иначе может завершиться ошибкой, которую легко не заметить в GUI-клиенте).

5. **Открыть Pull Request через compare-ссылку** (замените `<ваша-ветка>` на реальное имя):
   ```
   https://github.com/NazarJS/Pnewmo-next/compare/Nazz...Baldezhnik232:Pnewmo-next:<ваша-ветка>
   ```
   Открыть в браузере → GitHub соберёт diff и предложит создать PR из `Baldezhnik232/Pnewmo-next:<ваша-ветка>` в `NazarJS/Pnewmo-next:Nazz`.

6. **Дождаться ревью/мержа** от главного разработчика в PR — слияние в `Nazz` делает он сам через GitHub.

7. **После того как PR смержен** — синхронизировать локально:
   ```bash
   git fetch upstream
   git checkout Nazz-local-tracking-branch   # или любая ваша основная ветка
   git merge upstream/Nazz
   ```
   Ветку с фичей после мержа можно удалить (`git branch -d <ваша-ветка>`, `git push origin --delete <ваша-ветка>`).

## Чего никогда не делать (источник вчерашней путаницы)

- ❌ `git push upstream ...` — в любом виде, включая `HEAD:Nazz`. `upstream` — read-only.
- ❌ Мержить `upstream/*` прямо в ветку, которую вы не собираетесь пушить в `origin` — легко забыть, куда уехали изменения.
- ❌ Пушить без проверки текущей ветки (`git branch` / `git status` перед `push`) — вчерашняя ошибка началась с того, что оказались не на той ветке.

## Быстрая проверка перед любым push

```bash
git status            # какая ветка активна, чисто ли дерево
git remote -v          # origin — пушим сюда; upstream — только fetch
git log origin/<ветка>..HEAD --oneline   # что реально уедет
```
