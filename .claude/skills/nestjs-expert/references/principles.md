# Принципы: где чему место и почему

Примеры — из `apps/api`. Стайлгайд отвечает на вопрос «как написать»,
этот документ — на «почему именно так».

---

## SRP: одна причина для изменения

### Разделение по слоям

| Слой | Отвечает за | Не должен содержать |
|---|---|---|
| Контроллер | маршрут из контракта, маппинг в DTO | правил, запросов к базе, валидации |
| Сервис | бизнес-правила, оркестрацию | запросов к базе, HTTP-специфики, знания о статусах |
| Репозиторий | запросы Prisma, построение фильтров | правил домена, проверки прав |
| Контракт | форму запроса и ответа, валидацию | логики |

Проверка на практике — команда должна вернуть ровно одну строку, репозиторий:

```bash
grep -rn 'PrismaService' apps/api/src --include='*.ts' | grep -v generated | grep constructor
```

Кроме репозитория `PrismaService` упоминается только там, где определяется сам
(`prisma/prisma.service.ts`) и где объявляется провайдером (`prisma/prisma.module.ts`).
Появился в конструкторе сервиса — слой протёк.

### Правильно: сервис решает, репозиторий спрашивает

```ts
// categories.service.ts
async remove(id: number): Promise<{ id: number }> {
  await this.getById(id);

  const children = await this.repository.countChildren(id);

  if (children > 0) {
    throw new AppException(
      AppError.CONFLICT,
      `Нельзя удалить категорию: у неё ${children} подкатегорий`,
    );
  }

  const removed = await this.repository.remove(id);

  return { id: removed.id };
}
```

Сервис задаёт вопрос («сколько потомков») и принимает решение. Как именно посчитать —
дело репозитория.

### Неправильно: правило в контроллере

```ts
// ❌ Три нарушения сразу
@TsRestHandler(contract.categories.create)
create() {
  return tsRestHandler(contract.categories.create, async ({ body }) => {
    const existing = await this.repository.getBySlug(body.slug);   // репозиторий в обход сервиса
    if (existing) throw new AppException(AppError.CONFLICT, 'Занято'); // правило в контроллере
    return { status: 201, body: await this.repository.create(body) };  // сущность без маппинга
  });
}
```

### Неправильно: SQL в сервисе

```ts
// ❌ Запрос — ответственность репозитория
async getList() {
  return this.prisma.$queryRaw`SELECT * FROM categories`;
}
```

Сырой SQL допустим, но живёт в репозитории. Появится рекурсивный CTE для поддерева —
он будет методом `CategoriesRepository`, а не строкой в сервисе.

### Когда делить сервис

Больше 300 строк, больше пяти зависимостей в конструкторе, либо выделяется
самостоятельная вспомогательная логика. До этого — один файл. Заводить
`CategoriesUtilsService` на две функции незачем.

## DIP: зависеть от того, что можешь подменить

Сервис зависит от `CategoriesRepository`, а не от `PrismaService`. Практическое
следствие — юнит-тест без базы:

```ts
// categories.service.spec.ts
const stub: RepositoryStub = {
  getById: (id) => Promise.resolve(byId.get(id) ?? null),
  getParentId: (id) => {
    const row = byId.get(id);

    return Promise.resolve(row ? { parentId: row.parentId } : null);
  },
  countChildren: (id) => Promise.resolve(rows.filter((row) => row.parentId === id).length),
};
```

Восемь тестов на защиту от цикла выполняются без Postgres и без Nest — это и есть
практическая причина существования слоя репозитория, а не «так принято».

Отдельный интерфейс `ICategoriesRepository` при этом **не** заводится: класс сам служит
контрактом, а `Pick<CategoriesRepository, ...>` даёт заглушке типизацию. Интерфейс
появится, когда появится вторая реализация.

## KISS: простое решение, пока сложное не понадобилось

### Дерево собирается в памяти

Категорий сорок. Один плоский `SELECT` и сборка дерева на клиенте дешевле рекурсивного
запроса на каждый рендер меню. `WITH RECURSIVE` появится там, где понадобится «все товары
во всём поддереве» — то есть когда таблица товаров станет большой.

Вводить рекурсию сейчас значит оптимизировать запрос, которого нет.

### Пагинации нет

Сорок строк влезают в один ответ. `Pagination` появится вместе с товарами.

### Чего не делать

```ts
// ❌ Обёртка «чтобы можно было заменить ORM»
abstract class BaseRepository<T> {
  abstract findAll(): Promise<T[]>;
  abstract findOne(id: number): Promise<T | null>;
}
```

Теряются типизированные запросы Prisma, появляется протекающая абстракция, а ORM всё
равно никогда не меняется. То же про `BaseService` и фабрики без второй реализации.

## DRY: один источник правды, но не любое совпадение

### Что действительно нельзя дублировать

**Форма API.** Она описана в контракте один раз и оттуда же валидирует запрос на сервере
и типизирует клиент. Поэтому опечатка в имени поля ломает `pnpm typecheck`, а не
проявляется в рантайме.

**Схема обновления выводится из схемы создания:**

```ts
export const updateCategorySchema = createCategorySchema.partial();
```

Отдельный литерал разошёлся бы с исходной схемой при первой же правке.

### Где дублирование осознанное

Проверка потомков перед удалением повторяет `onDelete: Restrict` в базе. Это не
нарушение: ограничение в базе даёт общее сообщение про внешний ключ, а внятный текст
возможен только там, где известен домен. База остаётся страховкой от гонки — между
проверкой и удалением кто-то может добавить потомка.

Правило: дублировать **проверку** ради сообщения можно, дублировать **описание формы
данных** нельзя.

## Домен не знает про HTTP

`AppException` наследует `Error`, а не `HttpException`:

```ts
export class AppException extends Error {
  constructor(
    readonly code: AppError,
    message: string,
  ) {
    super(message);
    this.name = 'AppException';
  }
}
```

Статусы назначает единственный фильтр. Смысл границы: сервис можно вызвать не только из
HTTP-контроллера — из очереди, из планировщика, из скрипта — и он не потащит за собой
`BadRequestException`.

### NOT_FOUND против VALIDATION_FAILED

Не найден **запрашиваемый** ресурс — 404. Не найдено то, на что **ссылаются входные
данные** — 400: сам запрос некорректен, а не ресурс отсутствует.

```ts
// GET /categories/999 → 404
throw new AppException(AppError.NOT_FOUND, `Категория ${id} не найдена`);

// POST /categories { parentId: 999 } → 400
throw new AppException(AppError.VALIDATION_FAILED, `Родительская категория ${parentId} не найдена`);
```

## Строгая типизация

`any` не используется. Для данных неизвестной формы — `unknown` с явными проверками, как
в `extractTsRestIssues`: там разбирается тело чужого исключения, и каждое поле проверяется
перед использованием.

Приведение типа допустимо, когда система типов не может знать того, что знаем мы, и это
объясняется комментарием:

```ts
// Двойное приведение необходимо: у класса есть приватное поле prisma, поэтому
// структурного совпадения недостаточно.
return stub as unknown as CategoriesRepository;
```

`select` в репозитории — тоже инструмент типизации: невыбранные поля не существуют в
типе, поэтому отдать их наружу невозможно даже по ошибке.

## Что проверяет каждый вид теста

| Вид | Проверяет | Не проверяет |
|---|---|---|
| Юнит на сервис | бизнес-правила, с заглушкой репозитория | запросы к базе, HTTP |
| Юнит на чистые функции | маппинги ошибок | всё остальное |
| E2E | HTTP-контур целиком, против базы `pnewmo_test` | внутренние ветвления |

Тела ответов в e2e разбираются схемой контракта, а не проверяются по отдельным полям:
схема утверждает форму целиком, включая то, чего тест не читает.

Тест `points at the test database, not the dev one` существует не для проверки Prisma, а
чтобы прогон не уехал в рабочие данные: `beforeEach` вызывает `TRUNCATE`.
