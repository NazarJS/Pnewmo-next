# Этап 2: контекст проекта, скилл и ревьюер

Дата: 2026-08-11
Ветка: `dev`
Предыдущие этапы: `2026-08-11-monorepo-infra-design.md`, `2026-08-11-categories-backend-design.md`

## Зачем

Три этапа кода накопили конвенции, версионные ограничения и набор грабель, которые сейчас живут только в истории коммитов и спеках. Этап переносит их туда, где их найдут: в контекст проекта, в скилл и в ревьюера.

Порядок выбран сознательно — до этапа 3b. Ревьюер, написанный заранее, начинает приносить пользу с первого модуля фронтенда, а не после того как код разрастётся.

## Объём

### Входит

1. `.claude/CLAUDE.md` — точка входа вместо одной строки `@AGENTS.md`.
2. `.claude/context/backend-style-guide.md` — шаблоны кода по слоям, извлечённые из модуля `categories`.
3. `.claude/skills/nestjs-expert/SKILL.md` + `references/principles.md` + `references/patterns.md`.
4. `.claude/agents/backend-code-reviewer.md`.
5. `AGENTS.md` сокращается до правила про Next 16 и ссылки на `CLAUDE.md`; отчёт о сбое сборки переезжает в `docs/nextjs-build-incident.md`.

### Не входит

- **Фронтенд-ревьюер.** Отложен: осмысленные правила для фронтенда появятся после этапа 3b вместе с реальным кодом запросов, мутаций и формы. До тех тех пор фронтенд проверяется линтерами и глазами.
- **Фронтенд-стайлгайд.** Уже частично существует как скилл `component-structure`, писать второй документ поверх — дублирование.
- Скиллы под Prisma или ts-rest отдельно от `nestjs-expert`: разделять три файла на шесть при одном доменном модуле незачем.

## Размер по факту, а не по образцу

Стайлгайд в `panel-administration` — 632 строки, и там это оправдано: десятки модулей, каждый со своими паттернами. У нас **один** доменный модуль.

Написать 632 строки здесь означало бы выдумать примерно 500 из них — паттерны для кода, которого не существует. Это ровно то преждевременное абстрагирование, которое чеклист ревью запрещает. Поэтому каждый пример в стайлгайде берётся из существующего файла, с указанием откуда. Документ растёт вместе с проектом.

То же про `principles.md`: SOLID иллюстрируется нашими слоями, а не абстрактными `Feature`/`Entity`.

## `.claude/CLAUDE.md` — бюджет контекста

Файл грузится в **каждую** сессию, поэтому плотность важнее полноты. Правило разделения: в `CLAUDE.md` попадает только то, без чего можно сделать неверный шаг с первой попытки. Всё, что читается по необходимости, живёт в стайлгайде и скилле, а `CLAUDE.md` лишь указывает путь.

Содержание:

- что за проект, в одном абзаце;
- структура монорепо: три пакета и их роли;
- стек с версиями;
- **жёсткие ограничения**, каждое одной строкой: Node 24 (20 в EOL), Prisma 7 с драйвер-адаптером и почему примеры для 6 не работают, Zod пинится на 3.x, TypeScript на 5.x, `origin` — репозиторий тимлида и push не делается, `pnpm lint` падает на зафиксированном baseline;
- сохранённое из `AGENTS.md` правило про Next 16: версия ломающая, сверяться с `node_modules/next/dist/docs/`;
- куда смотреть дальше: `README.md` за командами, стайлгайд за шаблонами, `docs/superpowers/specs/` за решениями и их обоснованиями.

Команды в `CLAUDE.md` **не дублируются** — они в `README.md`, и два списка разойдутся.

## `.claude/context/backend-style-guide.md`

Десять разделов, каждый с примером из существующего кода:

| Раздел | Источник примера |
|---|---|
| Структура модуля | `apps/api/src/categories/` |
| Именование: файлы, классы, методы, таблицы | по факту кодовой базы |
| Prisma: схема, миграции, генерация клиента | `apps/api/prisma/schema.prisma`, `prisma.config.ts` |
| Репозиторий | `categories.repository.ts` |
| Сервис | `categories.service.ts` |
| Контроллер | `categories.controller.ts` |
| Контракт | `packages/api-contract/src/category.contract.ts` |
| Обработка ошибок | `common/errors/`, `common/filters/` |
| Тесты | `categories.service.spec.ts`, `categories.e2e-spec.ts` |
| Грабли окружения | история этапов 1 и 3a |

Ключевые правила, которые документ фиксирует как обязательные:

- `PrismaService` инжектится только в репозиторий; в сервисе его нет;
- репозиторий всегда с явным `select` — то, что не выбрано, невозможно случайно отдать клиенту;
- сущности Prisma не покидают контроллер, он маппит их в DTO контракта;
- сервис бросает `AppException` с кодом `AppError` и ничего не знает про HTTP-статусы;
- `PrismaModule` глобальный, репозитории домена — нет;
- узкие методы репозитория под конкретную задачу вместо универсальных: `getParentId` вместо выборки всей строки;
- юнит-тест сервиса работает с заглушкой репозитория, без базы; e2e — против отдельной базы `pnewmo_test`.

### Раздел «Грабли окружения»

Этого раздела нет в образце, и он самый полезный: каждый пункт стоил времени, а тут даёт ответ сразу.

- Prisma 7 против 6: генератор `prisma-client`, обязательный `output`, `moduleFormat = "cjs"`, генерация TypeScript вместо готового JS, обязательный драйвер-адаптер вокруг `pg.Pool`, `datasourceUrl` не работает.
- Jest и Prisma 7: `moduleNameMapper` срезает суффикс `.js` у относительных импортов, `NODE_OPTIONS=--experimental-vm-modules` для динамического импорта в рантайме Prisma.
- `tsBuildInfoFile` обязан лежать внутри `dist`: `deleteOutDir` в `nest-cli.json` удаляет сборку, но не состояние рядом с ней, и `nest build` начинает молча выдавать пустой `dist`, завершаясь успешно.
- Паттерн `.gitignore` со слешем в середине привязывается к каталогу самого файла: `src/generated/` не покрывает `apps/api/src/generated/`, нужен `**/src/generated/`.
- pnpm пробрасывает разделитель `--` дальше в команду, поэтому аргументы передаются без него: `pnpm db:psql -tAc 'select 1'`.
- Правя `packages/api-contract`, запускать `pnpm dev`, а не `pnpm --filter @pnewmo/api dev`: watch контракта поднимает только turbo, иначе отлаживается старая сборка.
- corepack на этой конфигурации сломан, pnpm ставится через `npm i -g pnpm@10`.
- Сгенерированный клиент Prisma не в git: после `pnpm install` на новой машине нужен `pnpm db:generate`, и `pnpm bootstrap` его уже вызывает.

## `.claude/skills/nestjs-expert/`

Структура повторяет образец, потому что она работает: `SKILL.md` навигационный, знания в `references/`.

`SKILL.md` — фронтматтер с описанием и ключевыми словами плюс таблица «какой файл читать когда»: `principles.md` для любой задачи по бэкенду, `patterns.md` дополнительно при создании модуля и при ревью.

`references/principles.md` — SOLID, KISS, DRY на наших слоях. Каждый принцип парой «правильно / неправильно» с кодом из проекта. Раздел про разделение ответственности по слоям — таблицей: что слой содержит и чего не должен.

`references/patterns.md` — порядок создания модуля, шаблоны методов сервиса и репозитория, антипаттерны, чеклист ревью. Антипаттерны берутся из образца там, где они не зависят от ORM (God Service, Leaky Abstraction, Circular Dependencies, Magic Strings, Silent Errors, Over-fetching, мутация входных параметров), и переписываются под Prisma там, где зависят.

### Таблица замен TypeORM → Prisma

Фиксируется в `patterns.md`, потому что образец целиком на TypeORM и без этой таблицы будет вводить в заблуждение:

| TypeORM | Prisma |
|---|---|
| `entities/{feature}.entity.ts` | папки нет, схема в `prisma/schema.prisma` |
| `FindOptionsWhere<Entity>` | `Prisma.CategoryWhereInput` |
| `In(ids)` | `{ id: { in: ids } }` |
| `ILike('%q%')` | `{ contains: q, mode: 'insensitive' }` |
| `Raw(alias => ...)` | `$queryRaw` с параметрами |
| `relations: [...]` | `include` / `select` |
| `findAndCount` | `$transaction([findMany, count])` |
| «Нет TypeORM в Service» | «Нет `PrismaService` в Service, только через Repository» |
| `synchronize: true` — антипаттерн | `prisma db push` на проде — антипаттерн, только `migrate deploy` |

Переносится без изменений: SRP и запрет логики в контроллере, маппинг в DTO, whitelist полей сортировки (это про инъекции, не про ORM), запрет `any`, `private readonly` для зависимостей, `Logger` в сервисах, запреты God Service, Silent Errors, мутации входных параметров и преждевременных абстракций.

## `.claude/agents/backend-code-reviewer.md`

Формат образца сохраняется: фронтматтер с `<example>`-блоками, нумерованный вывод с 🔴🟡🔵 и итоговой строкой. Нумерация важна практически — по номерам удобно говорить «поправь второй пункт».

Отличия от образца:

- **Границы:** `git diff HEAD -- 'apps/api/' 'packages/api-contract/'`. Фронтенд вне зоны ответственности.
- **Стек в проверках:** Prisma вместо TypeORM, ts-rest и Zod остаются.
- **Читает:** `.claude/context/backend-style-guide.md`, `.claude/skills/nestjs-expert/references/principles.md` и `patterns.md`.
- **Специфичные проверки нашего кода:** явный `select` в репозитории; отсутствие `PrismaService` в сервисе; маппинг в DTO в контроллере; `AppException` вместо `HttpException` в домене; e2e разбирают тело схемой контракта, а не отдельными полями.
- **Валидация находок:** через context7, затем официальная документация. Требование сохраняется: если документация не подтверждает — находка пересматривается, а не докладывается.
- **Знает про `validateResponses: true`**: несоответствие ответа контракту даёт 500, и это ожидаемое поведение, а не баг.

Инструменты в фронтматтере: `Bash`, `Read`, `Grep`, `Glob`, `WebFetch`, `WebSearch`, `ToolSearch` и оба инструмента context7.

Два отличия от образца, оба существенные. Имена инструментов context7 в этом проекте — `mcp__plugin_context7_context7__resolve-library-id` и `mcp__plugin_context7_context7__query-docs`; в образце указаны `mcp__context7__*`, которых здесь не существует, и агент с таким списком просто не получил бы доступа к документации.

`ToolSearch` добавляется потому, что инструменты MCP в этой конфигурации отложенные: их схемы подгружаются по требованию, и без `ToolSearch` вызов упадёт. Инструкция агента должна начинаться с загрузки схем context7 одним вызовом.

## `AGENTS.md` и отчёт о сбое

Сейчас `.claude/CLAUDE.md` состоит из строки `@AGENTS.md`, а `AGENTS.md` — отчёт об отладке сборки Next.js на 81 строку. То есть контекстом проекта служит история одного инцидента, причём её раздел про Turbopack мы уже пометили как устаревший в этапе 1.

Отчёт переезжает в `docs/nextjs-build-incident.md` без изменений содержания. Имя файла без даты: исходный документ её не содержит, а выдумывать не станем.

`AGENTS.md` остаётся коротким и содержит: правило про ломающую версию Next 16, ссылку на `.claude/CLAUDE.md` как на основной контекст, ссылку на переехавший отчёт.

Риск осознан: `AGENTS.md` писал NazarJS, и правка даст конфликт при merge его изменений. Конфликт будет маленьким и понятным — файл после правки короткий.

## Критерии готовности

1. `.claude/CLAUDE.md` не содержит `@AGENTS.md` как единственную строку и перечисляет все шесть жёстких ограничений.
2. Каждый блок кода в `backend-style-guide.md` либо снабжён путём к файлу, откуда он взят, либо явно помечен как пример антипаттерна. Блоков без источника и без пометки быть не должно — это проверяемо просмотром документа.
3. В `patterns.md` нет упоминаний TypeORM вне таблицы замен.
4. Файл агента содержит корректные имена инструментов context7 для этого проекта, сверенные со списком доступных инструментов.
5. `docs/nextjs-build-incident.md` существует, `AGENTS.md` короче 25 строк и ссылается на него.
6. Скилл проходит проверку из `superpowers:writing-skills`.
7. `pnpm lint`, `pnpm typecheck`, `pnpm build` не изменили поведение: этап не трогает исполняемый код.

## Замечание про план реализации

Этап целиком состоит из написания документов. План по правилам не содержит заглушек, то есть должен был бы включать полный текст каждого файла — и стал бы копией результата, написанной дважды.

Поэтому предлагается исполнять этап по этому спеку напрямую: он уже перечисляет файлы, их разделы и источники примеров, а проверяемым результатом служат сами файлы и критерии готовности выше. Если нужен отдельный план — он будет написан по запросу.
