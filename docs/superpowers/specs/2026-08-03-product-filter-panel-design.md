# Панель фильтрации товаров — дизайн

## Контекст и цель

На странице каталога (`app/catalog/[slug]/page.tsx`) нужна панель фильтрации товаров по их характеристикам (`specifications`). Товаров со временем станет много, поэтому фильтрация не должна работать по принципу «выгрузить все товары категории и отфильтровать в памяти» — это не масштабируется. Фильтрация должна выполняться на сервере (json-server), который отдаёт уже готовый отфильтрованный список.

Сейчас `specifications` — это `Record<string, string>` со значениями вида `"до 400 бар"`, `"500 мм"` (число и единица измерения слиты в одну строку). Такой формат нельзя фильтровать диапазоном на уровне json-server (`_gte`/`_lte` работают только по плоским числовым полям).

## Область задачи

- ✅ Фильтрация товаров каталога по характеристикам (`specifications`)
- ✅ Комбинация типов фильтров: диапазон (слайдер) для числовых характеристик, чекбоксы для категориальных
- ✅ Фильтры считаются специфичными для каждой категории (набор характеристик разный: у насосов — давление/расход/вес, у цилиндров — диаметр/ход штока)
- ❌ Универсальные поля цена/наличие/бренд — не входят в эту задачу (их сейчас нет в `db.json` вообще; добавление отложено)
- ❌ Пагинация списка товаров — не входит в эту задачу, но архитектура не должна ей мешать (см. «Открытые вопросы на будущее»)

## 1. Данные (`db.json` + типы)

К каждому товару рядом с уже существующим `specifications` (остаётся для отображения на странице товара, без изменений) добавляются плоские числовые поля вида `spec_<key>_value` — **только для характеристик-диапазонов**. Категориальные характеристики (`material`, `control` и т.п.) фильтруются точным совпадением по самому `specifications.<key>`, отдельное числовое поле им не нужно.

```json
{
  "id": "info_z2",
  "title": "Z2 — Станция насосная",
  "specifications": {
    "pressure": "до 400 бар",
    "flow": "до 2 л/мин",
    "weight": "25 кг"
  },
  "spec_pressure_value": 400,
  "spec_flow_value": 2,
  "spec_weight_value": 25
}
```

В `entities/product/model/types.ts` у `Product`/`ProductId` появляется индексная сигнатура:

```ts
interface Product {
  id: string;
  title: string;
  description: string;
  category_id: number;
  [key: `spec_${string}_value`]: number | undefined;
}
```

Набор ключей `spec_*_value` разный для разных категорий (пресс-формы, насосы, цилиндры имеют разные характеристики), поэтому строгая типизация по конкретным именам полей не подходит — только паттерн-сигнатура.

## 2. API-слой (`entities/product/api/products.api.ts`)

Два независимых запроса к json-server, каждый ограничен `category_id` (не всем каталогом целиком):

### a) Схема фильтров — `getCategoryFilterSchema(categoryIds: number[])`

Запрашивает товары категории **без фильтров** (`GET /products?category_id=10&category_id=11...`), сканирует их и строит схему:

```ts
type FilterField =
  | { type: "range"; key: string; label: string; unit?: string; min: number; max: number }
  | { type: "enum"; key: string; label: string; values: string[] };
```

- Поля-диапазоны определяются по наличию `spec_<key>_value` у товаров категории; `min`/`max` — фактические границы среди этих товаров.
- Категориальные поля — по ключам `specifications`, у которых нет соответствующего `spec_<key>_value`; `values` — уникальные строковые значения среди товаров категории.
- Человекочитаемые подписи и единицы измерения (`pressure` → «Давление», `бар`) берутся из статического словаря `SPEC_LABELS` в `entities/product` (это фиксированный технический словарь характеристик, не пользовательский ввод, поэтому хардкод уместен).

Схема считается от **полного набора товаров категории**, а не от уже отфильтрованного списка — иначе границы слайдера «плавали» бы при каждом изменении фильтра. Это отдельный, самостоятельный запрос.

### b) Отфильтрованный список — `getFilteredProducts(categoryIds: number[], filters: ProductFilters)`

Строит `URLSearchParams` и уходит в json-server:

- категории (OR): `category_id=10&category_id=11`
- диапазон: `spec_pressure_value_gte=100&spec_pressure_value_lte=400`
- категориальное точное совпадение: `specifications.material=сталь` (json-server поддерживает dot-notation для точного совпадения по вложенному полю)

Оба запроса решают проблему масштабирования: сервер получает только товары нужной категории и сразу агрегированные/отфильтрованные — полный каталог нигде не выгружается целиком.

## 3. Фича `product-filter` + интеграция со страницей каталога

Новый слой `src/features/` (первый в проекте) — по конвенции Feature-Sliced Design фильтрация товаров является бизнес-действием пользователя (фичей), а не просто секцией страницы, поэтому не подходит под `widgets`.

### `src/features/product-filter/`

- `model/types.ts` — `FilterField` (из схемы) и `ProductFilters` (текущее состояние: `{ [key]: { min: number; max: number } | string[] }`)
- `model/parseFiltersFromSearchParams.ts` — чистая функция `URLSearchParams → ProductFilters`
- `lib/buildFilterQueryParams.ts` — чистая функция `ProductFilters → URLSearchParams`, используется в `products.api.ts` при построении запроса к json-server
- `ui/ProductFilterPanel.tsx` (+ `ProductFilterPanel.module.scss`) — клиентский компонент (`"use client"`), рендерит по каждому полю схемы:
  - `type: "range"` → слайдер/два числовых инпута с границами `min`/`max` из схемы
  - `type: "enum"` → список чекбоксов по `values` из схемы

### Состояние — единственный источник истины: URL

Компонент не хранит список товаров и не хранит «выбранные фильтры» в отдельном React-состоянии, которое надо синхронизировать с сервером. Вместо этого:

1. Пользователь двигает слайдер / отмечает чекбокс.
2. `ProductFilterPanel` собирает новые query-параметры и вызывает `router.push` с обновлённым query-string (для слайдера — с дебаунсом ~300мс, чтобы не слать запрос на каждый пиксель перетаскивания).
3. Next.js перерисовывает страницу каталога как Server Component с новыми `searchParams` → она заново делает fetch уже отфильтрованного списка с json-server.

### `app/catalog/[slug]/page.tsx`

Остаётся серверным (async) компонентом, дополнительно принимает `searchParams`:

```
1. найти категорию по slug (как сейчас)
2. categoryIds = getChildCategoryIds(...)
3. filters = parseFiltersFromSearchParams(searchParams)
4. Promise.all([
     getCategoryFilterSchema(categoryIds),
     getFilteredProducts(categoryIds, filters),
   ])
5. рендер: <ProductFilterPanel schema={schema} activeFilters={filters} />
   рядом с сеткой товаров
```

## 4. Обработка ошибок и краевые случаи

- **Нет товаров в категории** — `getCategoryFilterSchema` возвращает пустой массив полей → `ProductFilterPanel` не рендерится вовсе.
- **Сбой запроса к json-server** — `getFilteredProducts`/`getCategoryFilterSchema` возвращают `null`, страница фолбэчит на `?? []`, тем же паттерном, что уже используется в `getProducts`/`getProductId`.
- **Битые/произвольные query-параметры в URL** (пользователь вручную подправил ссылку) — `parseFiltersFromSearchParams` молча игнорирует нераспознанные ключи и нечисловые значения диапазонов, не бросает исключение.
- **Пустые фильтры** (первый заход на страницу категории, ни один фильтр не тронут) — поведение идентично сегодняшнему списку без фильтров, регрессии нет.
- **Переход в другую категорию** — фильтры сами не переносятся, так как это новый `slug`-роут с чистыми `searchParams`; специальный код сброса не нужен.

## Открытые вопросы на будущее (вне текущей задачи)

- Универсальные фильтры (цена/наличие/бренд) — потребуют добавления этих полей в `db.json` и `Product` в отдельной задаче.
- Пагинация списка товаров — при добавлении должна использовать те же `searchParams` и тот же API-слой (`_page`/`_limit` к тому же запросу `getFilteredProducts`), чтобы не переделывать эти места повторно.
